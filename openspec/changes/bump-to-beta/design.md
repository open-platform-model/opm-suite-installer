## Context

See proposal.md for why. Three independent pin sites carry the OPM versions today:

- `Containerfile:18-20`: `OPM_VERSION=v1.0.0-alpha.20` plus one sha256 per architecture, checked
  with `sha256sum -c` before the binary is unpacked, and `opm version` run at the end of the step.
- `platform/`, `bundle/`, `modules/podinfo/` `cue.mod/module.cue`: core v2.0.0-alpha.10,
  catalogs/opm v4.4.0, catalogs/k8s v1.0.0-alpha.3 (platform only), `cue.dev/x/k8s.io` v0.11.0
  (platform only).
- `vendor/` + `vendor/VERSIONS`: generated by `hack/vendor-sync.sh` from the platform's pins,
  resolved against an empty private CUE cache with `platform/cue.mod/local-module.cue` removed.

The platform's pins are the ones that decide what gets vendored and rendered. The bundle's and
podinfo's core/catalog pins are nominal at render time (their `local-module.cue` replacements
point into `vendor/`), but a disagreement between them and the platform is confusing and would
surface the moment anyone evaluates a module on its own.

### Measured behavior

All runs on 2026-09-30 with `cue v0.17.1`, against scratch copies of `platform/`, `bundle/`,
`modules/podinfo/` and `vendor/` (probing with the newest already-published prereleases: core
v2.0.0-alpha.13, catalogs/opm v4.4.3, catalogs/k8s v1.0.0-alpha.6).

**`cue mod get` resolves from the registry, without the local replacements.**

```
$ (cd platform && cue mod get opmodel.dev/core@v2.0.0-alpha.13 \
    opmodel.dev/catalogs/opm@v4.4.3 opmodel.dev/catalogs/k8s@v1.0.0-alpha.6)   # exit 0
  -> cue.dev/x/k8s.io@v0 moved v0.11.0 -> v0.12.0, although local-module.cue redirects it
$ (cd modules/podinfo && cue mod get opmodel.dev/core@v2.0.0-alpha.13 \
    opmodel.dev/catalogs/opm@v4.4.3)                                             # exit 0
  -> adds cue.dev/x/k8s.io@v0 v0.12.0
$ (cd bundle && cue mod get opmodel.dev/core@v2.0.0-alpha.13)
cannot determine module graph: suite-installer.invalid/modules/podinfo@v0.1.10:
module suite-installer.invalid/modules/podinfo@v0.1.10: module not found
```

`cue.dev/x/k8s.io` is a dependency of `catalogs/opm` (its vendored `cue.mod/module.cue` declares
it; the k8s catalog's declares only core), so it moves with `catalogs/opm`.

**The CUE loader does honor `cue.mod/local-module.cue`.** It is CUE's own file, not an `opm`
convention (`cue mod edit --help`: "these edits are applied to cue.mod/local-module.cue"):

```
$ (cd bundle && cue vet -c ./...)
metadata.namespace: field is required but not present:
    ../vendor/opmodel.dev/core@v2/module_instance.cue:17:3     # loaded through the replacement
$ (cd bundle && rm cue.mod/local-module.cue && cue vet -c=false ./...)
import failed: cannot find package "opmodel.dev/core@v2": cannot expand module graph:
suite-installer.invalid/modules/podinfo@v0.1.10: module ... not found
```

So the bundle's placeholder dependency on the never-published podinfo module breaks only
`cue mod get`, which builds the graph from the registry; loading and vetting work.

**The bundle is incomplete by design, not broken.**

```
$ (cd platform && cue vet ./...)          # exit 0
$ (cd modules/podinfo && cue vet ./...)   # exit 0
$ (cd bundle && cue vet ./...)            # exit 1: "some instances are incomplete"
$ (cd bundle && cue vet -c=false ./...)   # exit 0
```

The missing field is `metadata.namespace`, which the entrypoint supplies at runtime from
`OPM_SUITE_NAMESPACE` as a generated file (AGENTS.md, the `-n` bullet). `bundle/` is therefore
checked with `-c=false`, and `task image:render` is the authoritative bundle check.

**`cue mod edit --require` works in the bundle but strips a load-bearing comment.**

```
$ (cd bundle && cue mod edit --require opmodel.dev/core@v2.0.0-alpha.13)   # exit 0
  -> core pin moved, podinfo placeholder and default: true kept,
     the comment above the podinfo dependency deleted
```

## Goals / Non-Goals

**Goals:**

- Every OPM input of the image is on the beta line, and `task check` plus a bare-cluster Job run
  still pass with the same rendered output as before (or a recorded, explained difference).
- Each pin is moved by the tool that owns it where one exists (`cue mod get`, `task vendor:sync`,
  the release's own `checksums.txt`), not typed.

**Non-Goals:**

- Adding this repo to the root `deps:update` / `deps:pins:opm-cli` tasks.
- Re-testing the 2026-09-22 "cluster Platform unusable" finding. The image installs CRDs only and
  never seeds a Platform; re-testing needs a full `opm operator install`, which is a separate
  experiment. The finding's precondition (the operator resolving core unpinned) has since been
  fixed upstream, so AGENTS.md qualifies the claim as measured on operator v1.0.0-alpha.14.
- Any behavior change to `scripts/opm-suite`, `deploy/` or the hooks.

## Script contract and RBAC delta

No script changes. `scripts/opm-suite` keeps its subcommands, arguments, environment variables
(`OPM_SUITE_NAMESPACE`, `OPM_SUITE_TIMEOUT`, ...) and exit codes (71, 74, 75, 76). The only
cluster-facing change is the CRD set `opm operator install --crds-only` applies: three CRDs in
`cli` v1.0.0-alpha.20, four in the beta line (adds `transformerregistrations.opmodel.dev`).

**RBAC delta: none.** The ClusterRole in `deploy/rbac.yaml` grants the CRD verbs without
`resourceNames`, so a fourth CRD needs no new rule. Task 4.1's cluster run verifies it: the
bootstrap fails with exit 71 if it does not hold.

## Decisions

**D1. `cue mod get` for platform and podinfo; bundle pins set by hand to match the platform.**
Platform and podinfo MUST move with `cue mod get` on exact versions (core, catalogs/opm, and in
platform catalogs/k8s), accepting the transitive pin (`cue.dev/x/k8s.io`) it writes. The bundle
cannot run `cue mod get` (measured above). Its core and catalogs/opm lines SHALL be set to the
exact versions the platform ended up with, and a verification step compares them. Alternatives
rejected:

- `cue mod edit --require` in `bundle/`: exits 0 and keeps `default: true`, but deletes the
  comment explaining why `default: true` is load bearing (measured). Losing that comment invites
  its removal later.
- Staging a bundle copy with the podinfo dependency removed, running `cue mod get` and splicing
  the placeholder back: the same two lines through more moving parts, still ending in a hand
  splice.

**D2. `vendor/` only through `task vendor:sync`.** AGENTS.md forbids hand edits; the script is the
one registry-touching action in the repo. `hack/vendor-sync.sh` builds the extract path as
`${dep%@*}@${version}`, which is version-string agnostic, so `-beta.1` should work; the task
MUST check it rather than assume it. The example version in the script's comment (lines 58-59)
moves to a beta string so a residual-`alpha` grep stays clean.

**D3. The `opm` pin is the G6 tag, with checksums from the release.** The target is the first `cli`
release that embeds operator v1.0.0-beta.1 (expected v1.0.0-beta.2; the real tag is recorded at
G6). The sha256 values MUST be copied from that release's `checksums.txt` and cross-checked by
hashing the downloaded tarballs; `podman build` re-checks them. A tag with no assets (the alpha.21
precedent) blocks the change rather than pinning an older tag: an older `cli` would embed a
pre-beta operator. `gh release view` without a tag currently reports `v0.6.0`, so the tag MUST
always be named explicitly.

**D4. podinfo adapts to core beta only when a check says so.** The jump is alpha.10 to beta.1
(four core prereleases). After vendoring, the three host vets (with `-c=false` in `bundle/`) and
the rendered-output diff against the baseline are the test. If they fail, the fix SHALL mirror
the reference podinfo, keeping this repo's `suite-installer.invalid` identity. The reference is
`cli/tests/fixtures/modules/podinfo` at the G6 `cli` tag, but only if its `cue.mod/module.cue`
pins the recorded core beta version (the fixture bump travels in a separate `test(fixtures)` PR,
and cli main pinned core alpha.6 on 2026-09-30); otherwise the reference is `cli/templates` at
the G4 tag. Nothing under `bundle/instances/` MAY gain a `metadata.namespace`: the namespace
arrives at runtime from `OPM_SUITE_NAMESPACE`, and a static one would change installer behavior.
The same rule applies to `platform/platform.cue` and `bundle/instances/podinfo/instance.cue`.

**D5. One PR, squash type `fix(deps)`.** The workspace commit skill types a bump by what ships
(never `chore`), and this repo ships the image. The repo has no release-please, no CI and
publishes nothing, so no commit type releases anything and no carrier footer exists. If D4
forces a module fix, it lands as its own inner commit (`fix(podinfo): ...`) in the same PR; the
squash stays `fix(deps)`.

**D6. Versions come from the gate lines, not from this document.** Each gate line records the
version actually published. If a version was burned upstream (the canon moves the target to
`-beta.2`), the tasks use the recorded value; `beta.1` and `4.4.4` in these artifacts are the
expected values.

## Risks / Trade-offs

- [G6 release lacks GoReleaser assets] → the change waits; the gate names the assets explicitly.
- [Core beta changes `#Platform` or `#registry` shape] → `platform.cue` fails `cue vet`; fix per D4
  and record it in `FINDINGS.md`.
- [`cue mod get` in podinfo adds `cue.dev/x/k8s.io` but the bundle's `local-module.cue` does not
  redirect it] → the offline render resolves through the platform's replacements, and
  `task image:render` (empty cache, `--network=none`) is exactly the proof that catches it.
- [Embedded CRDs change served version] → `MI_API` in `scripts/opm-suite` would be wrong; the
  cluster run reads it off the installed CRD.
- [The CR shape the rollout guard and revert read changes] → `.status.inventory.entries[]?` and
  `.spec.values` would silently read nothing and the guard would pass vacuously. The cluster run
  asserts both fields are present on the beta CRDs.
- [Semver ordering: `-dev.*` sorts above `-beta.N`] → exact versions only in every `cue mod get`;
  never `@latest` or a bare major.

## Migration Plan

None beyond the PR. Rollback is reverting the squash commit and rebuilding; nothing is published.
