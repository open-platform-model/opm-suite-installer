## Context

See proposal.md for why. Three independent pin sites carry the OPM versions today:

- `Containerfile:18-20`: `OPM_VERSION=v1.0.0-alpha.20` plus one sha256 per architecture, checked
  with `sha256sum -c` before the binary is unpacked, and `opm version` run at the end of the step.
- `platform/`, `bundle/`, `modules/podinfo/` `cue.mod/module.cue`: core v2.0.0-alpha.10,
  catalogs/opm v4.4.0, catalogs/k8s v1.0.0-alpha.3 (platform only), `cue.dev/x/k8s.io` v0.11.0
  (platform only).
- `vendor/` + `vendor/VERSIONS`: generated by `hack/vendor-sync.sh` from the platform's pins,
  resolved against an empty private CUE cache with `platform/cue.mod/local-module.cue` removed.

The platform's pins are the ones that decide what gets vendored and rendered. The bundle's and
podinfo's core/catalog pins are nominal at render time (their `local-module.cue` replacements
point into `vendor/`), but a disagreement between them and the platform is confusing and would
surface the moment anyone evaluates a module on its own.

Measured on 2026-09-30 with `cue v0.17.1`, against scratch copies of the three directories
(probing with the already-published core v2.0.0-alpha.13):

```
$ (cd platform && cue mod get opmodel.dev/core@v2.0.0-alpha.13)        # exit 0, pin moved
$ (cd modules/podinfo && cue mod get opmodel.dev/core@v2.0.0-alpha.13) # exit 0, pin moved,
                                                                      # adds cue.dev/x/k8s.io@v0 v0.11.0
$ (cd bundle && cue mod get opmodel.dev/core@v2.0.0-alpha.13)
cannot determine module graph: suite-installer.invalid/modules/podinfo@v0.1.10:
module suite-installer.invalid/modules/podinfo@v0.1.10: module not found
```

`cue` does not read `cue.mod/local-module.cue` (that file is an `opm` convention), so the bundle's
placeholder dependency on the never-published podinfo module makes `cue mod get` unusable there.

## Goals / Non-Goals

**Goals:**

- Every OPM input of the image is on the beta line, and `task check` plus a bare-cluster Job run
  still pass.
- Each pin is moved by the tool that owns it where one exists (`cue mod get`, `task vendor:sync`,
  the release's own `checksums.txt`), not typed.

**Non-Goals:**

- Adding this repo to the root `deps:update` / `deps:pins:opm-cli` tasks.
- Re-testing the 2026-09-22 "cluster Platform unusable" finding. The image installs CRDs only and
  never seeds a Platform; re-testing needs a full `opm operator install`, which is a separate
  experiment.
- Any behavior change to `scripts/opm-suite`, `deploy/` or the hooks.

## Decisions

**D1. `cue mod get` for platform and podinfo; bundle pins set to match the platform.** Platform and
podinfo move with `cue mod get opmodel.dev/core@v2.0.0-beta.1 opmodel.dev/catalogs/opm@v4.4.4`
(plus `opmodel.dev/catalogs/k8s@v1.0.0-beta.1` in platform), accepting whatever transitive pins
(`cue.dev/x/k8s.io`) it writes. The bundle cannot run `cue mod get` (measured above), so its two
core/catalog lines are set to the exact versions the platform ended up with, and a verification
step compares them. Alternative rejected: staging a bundle copy with the podinfo dependency
removed, running `cue mod get`, and splicing the placeholder back. It produces the same two lines
through more moving parts and still ends in a hand splice.

**D2. `vendor/` only through `task vendor:sync`.** AGENTS.md forbids hand edits; the script is the
one registry-touching action in the repo. `hack/vendor-sync.sh` builds the extract path as
`${dep%@*}@${version}`, which is version-string agnostic, so `-beta.1` should work; the task checks
it rather than assuming it. The example version in the script's comment (lines 58-59) moves to a
beta string so a residual-`alpha` grep stays clean.

**D3. The `opm` pin is the G6 tag, with checksums from the release.** The target is the first `cli`
release that embeds operator v1.0.0-beta.1 (expected v1.0.0-beta.2; read the real tag at G6). The
sha256 values are copied from that release's `checksums.txt` and cross-checked by hashing the
downloaded tarballs; `podman build` re-checks them. A tag with no assets (the alpha.21 precedent)
blocks the change rather than pinning an older tag: an older `cli` would embed a pre-beta operator.
`gh release view` without a tag currently reports `v0.6.0`, so the tag is always named explicitly.

**D4. podinfo adapts to core beta only when a render says so.** The jump is alpha.10 to beta.1
(four core prereleases). After vendoring, `task image:render` and a host `cue vet ./...` per module
are the test. If they fail, the fix mirrors `cli/tests/fixtures/modules/podinfo` at the G6 `cli`
tag (the module was copied from there), keeping this repo's `suite-installer.invalid` identity. The
same applies to `platform/platform.cue` and `bundle/instances/podinfo/instance.cue`.

**D5. One PR, squash type `chore(deps)`.** The repo has no release-please, no CI and publishes
nothing, so no commit type releases anything and no carrier footer exists. `chore(deps)` matches
what the change is. If D4 forces a module fix, it lands as its own inner commit
(`fix(podinfo): ...`) in the same PR; the squash stays `chore(deps)`.

## Risks / Trade-offs

- [G6 release lacks GoReleaser assets] → the change waits; the gate names the assets explicitly.
- [Core beta changes `#Platform` or `#registry` shape] → `platform.cue` fails `cue vet`; fix per D4
  and record it in `FINDINGS.md`.
- [`cue mod get` in podinfo adds `cue.dev/x/k8s.io` but the bundle's `local-module.cue` does not
  redirect it] → the offline render resolves through the platform's replacements, and
  `task image:render` (empty cache, `--network=none`) is exactly the proof that catches it.
- [Embedded CRDs change served version] → `MI_API` in `scripts/opm-suite` would be wrong; the
  cluster run reads it off the installed CRD.
- [Semver ordering: `-dev.*` sorts above `-beta.N`] → exact versions only in every `cue mod get`;
  never `@latest` or a bare major.

## Migration Plan

None beyond the PR. Rollback is reverting the squash commit and rebuilding; nothing is published.
