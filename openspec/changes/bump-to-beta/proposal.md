## Why

The OPM stack is cutting its first beta: `opmodel.dev/core@v2` 2.0.0-beta.1, `catalogs/k8s`
1.0.0-beta.1, `catalogs/opm` 4.4.4 built on that core, and a `cli` release that embeds
`opm-operator` v1.0.0-beta.1. This repo sits outside every root pin task (`deps:update`,
`deps:pins:opm-cli`), so it stays on `opm` v1.0.0-alpha.20 and core v2.0.0-alpha.10 unless it is
moved by hand. A proof of concept whose findings are measured against an alpha nobody runs any
more stops answering its question.

This change answers: **does the self-contained installer image still build, render offline and
install podinfo on a bare cluster when every OPM input is on the beta line?** A "no" (for
example, core beta forcing a module change the bundled podinfo cannot absorb in bash-free CUE)
is a finding worth recording, not a failure of the change.

Alternatives not chosen:

- **Do nothing.** The image keeps working against alpha pins, but every future finding would be
  about a line the rest of the workspace has left, and the embedded operator CRDs would diverge
  from what the beta operator serves.
- **Add this repo to the root `deps:update` / `deps:pins:opm-cli` tasks first.** It would make
  later bumps mechanical, but it is a workspace tooling change with its own review, and the
  installer's pin model (tarball sha256 plus a committed `vendor/` tree) does not fit either
  task's shape today. Left as an open question, not blocked on.

## What Changes

- `Containerfile`: `ARG OPM_VERSION` moves to the first `cli` release that embeds
  `opm-operator` v1.0.0-beta.1 (gate G6, expected v1.0.0-beta.2; the real tag is read at G6),
  and both `OPM_SHA256_AMD64` / `OPM_SHA256_ARM64` come from that release's `checksums.txt`. The
  comment explaining the alpha.20-over-alpha.21 choice is replaced by the current rationale.
- `platform/`, `bundle/`, `modules/podinfo/` `cue.mod/module.cue`: `opmodel.dev/core@v2` to
  v2.0.0-beta.1, `opmodel.dev/catalogs/opm@v4` to v4.4.4, and (platform only)
  `opmodel.dev/catalogs/k8s@v1` to v1.0.0-beta.1. `cue.dev/x/k8s.io@v0` follows whatever the k8s
  catalog requires.
- `vendor/` and `vendor/VERSIONS` regenerated by `task vendor:sync`; never hand-edited.
- The bundled podinfo module, its instance and the baked platform are adapted to core beta only
  if the jump from alpha.10 requires it (checked, not assumed).
- `AGENTS.md` (the glibc/pin bullet, around line 189) states the current pin.
- `FINDINGS.md` gains one new dated entry recording what the move required. Existing entries
  are history and are not rewritten.

No installer behavior changes: exit codes, subcommands, stdout/stderr contracts, RBAC and the
second-run behavior in `openspec/specs/` all stay as they are. The change therefore carries no
spec delta (`skip_specs: true`). If the bump forces a behavior change, that is a new change.

`opm` can do everything this needs (Principle II): the bump is pins, vendored source and a
rebuilt image.

## Capabilities

### New Capabilities

None.

### Modified Capabilities

None. Spec-level behavior (`bundle-render`, `bundle-apply`, `bundle-lifecycle`) is unchanged;
`skip_specs: true` is set in `.openspec.yaml`.

## Impact

- **Image:** a new `opm` binary (and with it the embedded CRD manifest `opm operator install
  --crds-only` applies) and a new vendored CUE tree. Image size may move; measured and recorded.
- **Cluster:** the CRDs the Job installs come from operator v1.0.0-beta.1. The `ModuleInstance`
  API is expected to stay `opmodel.dev/v1alpha1` (the CRD API does not move until GA);
  `scripts/opm-suite` hardcodes it, so it is re-read off the installed CRD, not assumed.
- **Upstream gates:** G1 (core beta on GHCR), G3 (catalogs on GHCR) and G6 (the `cli` release
  embedding the beta operator, with GoReleaser assets). Nothing here publishes or releases: the
  repo has no release-please and no CI.
- **Scope:** one capability-free pin move, one PR. Root workspace tasks are not involved.
